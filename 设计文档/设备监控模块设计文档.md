## 一、模块概述

### 1.1 功能目标

在系统的「系统管理」菜单下新增一个设备监控子模块，用于：

- **监控设备在线状态**：实时查看各 RTU 设备是否在线、最近通讯时间
- **监控数据采集状态**：判断各监测点位的数据采集是否正常（检测硬件采集数据异常）
- **自动记录故障**：设备离线或采集异常时自动生成故障记录
- **人工处理故障**：管理人员可查看历史故障、填写处理记录

### 1.2 设计原则

- **不重复存储采集数据**：采集数据已在其他模块展示，监控模块只关注"设备是否在线"和"采集是否正常"
- **利用现有数据**：充分利用 collector 库 `t_rtu_baseinfo` 表中已有的 `ONLINE`、`LATEST_TM`、`WARN_VAL` 字段
- **故障去重**：同一设备的同一故障在未恢复前不重复记录
- **可扩展**：已实现 `offline`（通讯离线）和 `no_data`（硬件采集数据异常）两种故障类型，后续可扩展更多

### 1.3 技术栈

## 二、数据结构设计

### 2.1 核心依赖表（已有，在 collector 库）

#### t_rtu_baseinfo — RTU 设备基础信息

该表由数据采集系统维护，是本模块的核心数据来源。

| 字段名 | 类型 | 说明 | 用途 |
|--------|------|------|------|
| `RTUCD` | varchar(30) PK | RTU编码，设备唯一标识 | 关联设备 |
| `STCD` | varchar(10) UNIQUE | 测站编码 | 关联采集数据 |
| `STNM` | varchar(30) | 测站名称 | 前端展示 |
| `LATEST_TM` | datetime | 最近通讯时间 | 判断通讯是否超时 |
| `ONLINE` | char(1) | 是否在线：1-在线 0-离线 | 核心判断依据 |
| `WARN_VAL` | decimal(3,1) | 通讯预警值(小时) | 超过此时间未通讯视为异常 |
| `STLC` | varchar(200) | 站址 | 前端展示 |

**关键逻辑**：`ONLINE` 和 `LATEST_TM` 由数据采集系统（RTU 接收服务）实时更新，本模块只读取不写入。

> **为什么不用新建状态表？** 因为 `t_rtu_baseinfo` 已经包含了所有必要的设备状态信息（在线标志、最后通讯时间、预警阈值），再建一张状态表就是数据冗余。

#### t_rtu_baseinfo_extend — 设备扩展信息（辅助表）

用于判断设备类型，确定该设备应该查哪张采集表。

| 字段名 | 说明 | 用途 |
|--------|------|------|
| `RTUCD` | RTU编码 | 关联 t_rtu_baseinfo |
| `GROUP_ID` | 分组ID，逗号分隔（如",2,3,"） | 判断设备类型：1=水位 2=流量 3=视频 |
| `STTP` | 站点类型编码 | 补充判断设备协议类型（48=水资源 WR=水文） |

#### t_rtu_groupinfo — 设备分组定义

| GROUP_ID | NAME | 说明 |
|----------|------|------|
| 1 | 水位 | 水位监测设备 |
| 2 | 流量 | 流量监测设备 |
| 3 | 视频 | 视频监控设备（暂不纳入巡检） |

#### 采集表 — 设备数据存储（collector 库）

**各设备类型对应的采集表：**

| 设备分组 | 采集表 | 编码字段 | 数据类型 | 说明 |
|---------|--------|---------|---------|------|
| 流量(2) | `st_river_r` | `STCD` | 河流水文数据 | 含瞬时流量(Q1)、水位(Z1)、累计流量(SL1)等 |
| 流量(2) | `wr_mp_q_r` | `MP_CD` | 水资源流量监测 | 独立流量计数据，与 STCD 同编码体系 |
| 水位(1) | `wr_mp_z_r` | `MP_CD` | 水资源水位监测 | 独立水位计数据 |
| 水质 | `bb` | 无标准编码 | 水质监测 | 存储在 eb_database 远程库，本地开发不可用 |

**STCD 与 MP_CD 的关系：**

从 `RiverCollectorServiceImpl.syncFlowData()` 的代码可知：
```java
flow.setMpCd(collector.getStcd());  // 把 st_river_r 的 STCD 作为 MP_CD 存入
```

STCD 和 MP_CD 使用**同一套测站编码体系**，可以等同对待。因此在 `no_data` 检测中，设备的 `t_rtu_baseinfo.STCD` 可以同时去查 `st_river_r.STCD` 和 `wr_mp_*.MP_CD`。

**视频设备不纳入巡检：** GROUP_ID 包含 3（视频分组）的设备仅用于视频监控，无采集数据表，自动跳过 `no_data` 检测。

### 2.2 新增表（在 gcdd 库）

#### device_fault_history — 设备故障历史记录

故障记录表，由定时任务自动写入，管理人员可手动处理。

| 字段名 | 类型 | 说明 | 业务含义 |
|--------|------|------|----------|
| `id` | bigint PK AUTO | 主键 | 自增ID |
| `device_code` | varchar(50) | 设备编码(RTUCD) | 关联 t_rtu_baseinfo |
| `device_name` | varchar(100) | 设备名称 | 冗余，方便展示，避免联表 |
| `device_type` | varchar(30) | 设备类型 | 预留字段 |
| `fault_type` | varchar(30) | **故障类型** | 见下方枚举 |
| `fault_description` | varchar(500) | 故障描述 | 自动生成的故障说明 |
| `fault_time` | datetime | 故障发生时间 | 检测到故障的时间 |
| `recovery_time` | datetime | 恢复时间 | 自动或人工填写 |
| `status` | varchar(20) | **处理状态** | 见下方枚举 |
| `handler` | varchar(50) | 处理人 | 人工填写 |
| `handle_method` | varchar(500) | 处理方式 | 人工填写 |
| `handle_time` | datetime | 处理时间 | 人工提交时自动记录 |
| `create_time` | datetime | 创建时间 | 自动填充 |
| `update_time` | datetime | 更新时间 | 自动填充 |

**故障类型枚举（fault_type）：**

| 代码值 | 含义 | 触发条件 | 实现状态 |
|--------|------|----------|----------|
| `offline` | 通讯离线 | `ONLINE='0'` 或最后通讯时间超过24小时 | ✅ 已实现 |
| `no_data` | 硬件采集数据异常 | 设备在线但采集表（如 st_river_r）**超过2小时**无新数据 | ✅ 已实现 |

**处理状态枚举（status）：**

| 代码值 | 含义 | 改变途径 |
|--------|------|----------|
| `active` | 未恢复 | 定时任务新增故障时自动设置 |
| `resolved` | 已恢复 | 自动：设备恢复在线 |

**索引说明：**

| 索引名 | 字段 | 用途 |
|--------|------|------|
| `idx_device_code` | device_code | 点击设备行查询该设备所有故障时加速 |
| `idx_status` | status | 按处理状态筛选时加速 |
| `idx_fault_time` | fault_time | 按时间倒序排列时加速 |

### 3.3 数据源策略

| 数据源 | 库名 | 用途 | 使用方式 |
|--------|------|------|----------|
| `collector` | collector | 读取 t_rtu_baseinfo 设备状态 | @DS("collector") |
| `gcdd` | gcdd | 读写 device_fault_history 故障记录 | 默认数据源 |

**为什么故障表放 gcdd 不放 collector：**
- gcdd 是本系统的业务主库，故障记录是本系统的业务数据
- collector 库由独立的采集系统管理，可能被重置或迁移
- 保持故障记录与业务数据的生命周期一致

### 3.4 定时巡检逻辑（核心）

```java
// 位于 DataSyncTask.java — 简化示意，以实际代码为准
@Scheduled(cron = "0 0/5 * * * ?")
public void monitorDeviceStatus() {
    List<RtuBaseInfo> deviceList = rtuBaseInfoMapper.selectList(null);
    Date now = new Date();

    // 预查所有采集表中近2小时内有数据的测站编码（合并多表结果）
    Set<String> stationCodesWithData = queryStationCodesWithRecentData(now);

    for (RtuBaseInfo device : deviceList) {
        checkDevice(device, now, stationCodesWithData);
    }
}

/**
 * 合并查询 3 张采集表，返回近2小时内有数据的测站编码集合。
 * 只要任意一张表有该站的数据，就不算 no_data。
 */
private Set<String> queryStationCodesWithRecentData(Date now) {
    long twoHoursAgo = now.getTime() - 2 * 3600 * 1000L;
    Set<String> codes = new HashSet<>();

    // 1. 从 st_river_r 查（流河水文表，用 STCD）
    riverCollectorMapper.selectLastRecord().stream()
        .filter(r -> r.getTm() != null && r.getTm().getTime() >= twoHoursAgo)
        .map(RiverCollector::getStcd).forEach(codes::add);

    // 2. 从 wr_mp_q_r 查（流量监测，用 MP_CD）
    flowCollectorMapper.selectLastRecord().stream()
        .filter(f -> f.getTm() != null && f.getTm().getTime() >= twoHoursAgo)
        .map(FlowCollector::getMpCd).forEach(codes::add);

    // 3. 从 wr_mp_z_r 查（水位监测，用 MP_CD）
    waterLevelCollectorMapper.selectLastRecord().stream()
        .filter(l -> l.getTm() != null && l.getTm().getTime() >= twoHoursAgo)
        .map(WaterLevelCollector::getMpCd).forEach(codes::add);

    return codes;
}

private void checkDevice(device, now, stationCodesWithData) {
    // === offline 检测 ===
    if (ONLINE == '0' || 当前时间 - LATEST_TM > 24小时) {
        if (没有未恢复的离线故障) { insertFault("offline", ...); }
        return;  // 已离线，跳过 no_data
    }

    // 设备在线，恢复旧离线故障
    if (有未恢复的离线故障) { autoResolve("offline"); }

    // === no_data 检测 ===
    if (设备的STCD 不在 stationCodesWithData 中) {
        if (没有未恢复的no_data故障) { insertFault("no_data", ...); }
    } else {
        if (有未恢复的no_data故障) { autoResolve("no_data"); }
    }
}
```

**流程图：**
```
开始巡检
    │
    ▼
获取所有设备 (t_rtu_baseinfo)
    │
    ▼
查询采集表有数据的 STCD 集合
    │
    ▼
遍历每台设备
    │
    ├──→ ONLINE=0 或 通讯超时？
    │        │
    │        ├──→ 已有活跃离线故障？ ──→ 跳过（去重）
    │        │
    │        └──→ 无活跃离线故障  ──→ 新增 offline 故障
    │
    └──→ 设备在线
             │
             ├──→ 有活跃离线故障？ ──→ 自动恢复
             │
             ├──→ STCD 不在采集表中？
             │        │
             │        ├──→ 已有活跃 no_data 故障？ ──→ 跳过
             │        │
             │        └──→ 无活跃 no_data 故障  ──→ 新增 no_data 故障
             │
             └──→ STCD 在采集表中？
                      │
                      ├──→ 有活跃 no_data 故障？ ──→ 自动恢复
                      │
                      └──→ 无活跃故障  ──→ 跳过（正常状态）
```

**关键设计点：**
- **每5分钟执行一次**：与现有的数据同步任务频率一致
- **去重机制**：同一设备连续多次巡检都为同一故障时，只会在第一次插入故障记录，后续不会重复插入
- **自动恢复**：设备恢复后，第一个巡检周期就会自动将故障标记为已恢复
- **WARN_VAL 默认值**：24小时（如果数据库中该字段为空）
- **同步与巡检分离**：`monitorDeviceStatus()` 先执行数据同步，再执行状态巡检，确保 `no_data` 判断基于最新数据

**no_data 检测策略（多表合并）：**

```
queryStationCodesWithRecentData(now):
    │
    ├── 查 st_river_r  → 取所有 STCD (近2小时有数据)
    ├── 查 wr_mp_q_r   → 取所有 MP_CD (近2小时有数据)
    └── 查 wr_mp_z_r   → 取所有 MP_CD (近2小时有数据)
    │
    └── 合并为 Set<测站编码>

checkDevice(device):
    │
    └── 设备.STCD ∈ Set ？
        ├── 是 → 数据正常，恢复 no_data 故障
        └── 否 → 新增 no_data 故障
```

**2 小时阈值说明：** 采集数据每5分钟同步一次，正常情况下最新数据延迟不超过5分钟。设2小时（120分钟）的阈值远大于正常延迟，目的是：
- 避免偶发性的单次采集延迟导致误报
- 留出足够时间让运维人员处理问题
- 与 `offline` 的24小时阈值形成梯度：先报 no_data，持续恶化才报 offline

### 4.4 后端 API 调用方式

所有请求通过 axios 实例 `this.$http` 发送。前端进页面时调用合并接口 `/overview`，一次请求同时获取统计和列表：

```js
// 初始加载：一次请求获取统计+列表，代替原来的两次独立请求
const { data: res } = await this.$http.get('/deviceMonitor/overview', {
  params: { currentPage: 1, pageSize: 10 }
})
// res.data.statistics = { total, onlineCount, offlineCount }
// res.data.deviceList.records = 设备列表
// res.data.deviceList.total = 设备总数
```

翻页时直接调用 `/list`，使用"先请求后更新"策略避免闪现：

```js
// 翻页：先发请求，数据到达后再更新页码，保证序号和数据同步
async handleCurrentChange(newPage) {
  const { data: res } = await this.$http.get('/deviceMonitor/list', {
    params: { currentPage: newPage, pageSize: this.queryInfo.pageSize }
  })
  this.queryInfo.currentPage = newPage  // 数据到了再更新
  this.deviceList = res.data.records
}
```

## 六、扩展指南

### 6.1 扩展采集表检测范围

目前 `no_data` 检测覆盖了 3 张采集表：

| 表名 | 编码字段 | 数据类型 | Mapper |
|------|---------|---------|-------|
| `st_river_r` | STCD | 流量+水位 | RiverCollectorMapper |
| `wr_mp_q_r` | MP_CD | 流量监测 | FlowCollectorMapper |
| `wr_mp_z_r` | MP_CD | 水位监测 | WaterLevelCollectorMapper |

如果想增加更多采集表（如水质表 `wq_awqmd_d`），修改 `DataSyncTask.queryStationCodesWithRecentData()` 方法，按同样的模式增加查表逻辑即可。

### 6.2 新增设备类型分组

如果想按设备类型（水位站、流量站、水质站）筛选：

1. **后端**：`DeviceMonitorServiceImpl.listDevices()` 中增加 `deviceType` 参数过滤，关联 `t_rtu_baseinfo_extend.STTP`
2. **前端**：`DeviceMonitor.vue` 增加设备类型下拉框
3. **Mapper**：如果需要复杂查询，在 `RtuBaseInfoMapper.xml` 中写自定义SQL

### 6.3 新增告警通知

可以在 `DataSyncTask` 的故障生成逻辑中增加通知机制：

```java
// 新增故障时，同时发送通知
if (!hasActiveOfflineFault) {
    // 1. 保存故障记录
    deviceFaultHistoryService.save(fault);
    // 2. 发送通知（以下方式任选）
    smsService.sendSms(adminPhone, "设备" + deviceName + "离线");
    // 或 写入预警信息表
    warningInformationService.save(warning);
}
```

## 九、常见问题

**Q: 设备监控页面没有显示任何设备？**
A: 检查 collector 库的 `t_rtu_baseinfo` 表是否有数据。这是页面的唯一数据来源。

**Q: 历史故障页面没有记录？**
A: 初始状态下确实没有记录。故障由定时任务每5分钟检测生成。可以：
- 手动在 `device_fault_history` 表插入几条测试数据
- 或者等定时任务检测到离线设备后自动生成

**Q: 新增的菜单看不到？**
A: 需要同时满足两个条件：
1. 菜单数据已插入 `authority` 表
2. 当前登录用户的角色已关联该菜单权限（见 `role_authority` 表）

**Q: 报错 eb_database 连接失败？**
A: `application.yml` 中 `eb_database` 配置的是远程服务器IP，本地开发时注释掉即可。
